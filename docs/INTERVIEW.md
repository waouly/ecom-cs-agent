# 面试答辩手册：电商智能客服 Agent

用法：左边是会被问到的，右边是**一句话结论 + 两句话展开**。所有数字都能在仓库里复现（命令在每节末尾）。

---

## 一、30 秒版本

「我把简历上的电商客服系统做了一次重构：原版解决的是『资料找不到』，新版解决的是『这单能不能退、怎么退』。核心是把政策条款从长文本变成可执行的条件 DSL，规则引擎三值求值给出确定结论，模型只负责把结论说成人话；生成之后还有 claim 逐句核验、数字溯源和合规拦截；决策从『答/转人工』变成『答/追问/转人工』三选一；最后用概率校准加保形阈值控制自动答复的错误率。离线可跑，30 条端到端评测四个维度全过，54 个单测。」

---

## 二、为什么重做，原版不行吗

**结论**：原版不是不行，是优化错了对象。

- 原版指标是 Recall@5 98%、MRR 0.894——这在「资料检索」里是很有说服力的数字。但客服的真实失败不是「没找到条款」，而是「找到了条款，结论说错了，或者该追问时硬答」。
- 举例：用户问「数码产品拆封了还能退吗」。检索能召回七天无理由条款，但条款里「未拆封」是前置条件，模型不一定会去核对；即使核对了，它也可能编一个「可以退，但需支付 20% 折旧」——原版没有任何机制拦这句话。
- 所以新版的第一性指标不是召回率，而是**决策正确率**和**回答可核验率**。

## 三、政策 DSL 具体长什么样，为什么不用 prompt 让模型判断

**结论**：因为「同一问题两次回答不一致」在客服里是事故，不是体验问题。

- 一条条款 = `applies_to`（适用类目）+ `conditions`（字段/操作符/值）+ `exceptions`（例外覆盖）+ `action`（处置动作）。引擎三值求值：真 / 假 / **未知**。
- 「未知」是关键：它携带 `missing` 字段名，直接驱动追问（「商品拆封了吗」），而不是让模型猜。
- 例外命中会覆盖基础条件（质量问题优先于七天无理由）；违反项是确定性的（拆封、定制）就直接拒绝，不确定（超期仍可能走质量问题）才追问。
- 代价要说清楚：政策要能结构化建模，运营改政策要改 JSON；复杂阶梯/地区规则当前表达不了，这是明确的边界。

**追问预案**：「那模型还干什么？」——模型做三件事：把判定结论自然语言化、把用户口语归一化/改写、处理闲聊与安抚。判断本身不交给模型。

## 四、置信度凭什么可信

**结论**：不是我拍的阈值，是校准过的概率 + 有覆盖率保证的阈值。

1. 融合分来自四个可解释信号：top1 相关性、top1/top2 的 margin、意图置信度、工具完备度，政策状态再加权。
2. Platt 校准把融合分映射成「答对概率」（当前样本 30 条拟合出 a≈2.3、b≈4.6）。
3. 保形阈值按「错误率 ≤ alpha」扫出最小阈值（当前 0.529，coverage 0.60，risk 0.000）。
4. 加了 `floor=0.5` 的工程下限：否则样本全对时公式会退化成「0 分也自动答」。

**诚实边界**：30 条样本的校准曲线只能证明流程正确，不能证明概率精确。上线需要几百到几千条标注样本；分布漂移后要滚动重拟合。

**追问预案**：「为什么不用 LLM 自评置信度？」——自评分数不可校准（模型普遍过自信），且不可解释；我宁可要一个能画 reliability diagram 的信号。

## 五、生成后核验会不会误杀正确回答

**结论**：会，所以核验器必须知道「哪些事实是引擎算的」。

- claim 核验拿检索证据算覆盖度，会误杀两类正确回答：规则引擎的结论（「因此您可以申请全额退款」）和工具事实（「订单 O10004 已签收」）。
- 解法是做 `trusted` 通道：引擎的满足项/违反项、工具返回的短标量（2–24 字符）进白名单，命中即判 `engine_fact`；同时把条款正文、工具数据摊平进 `extras` 参与覆盖度计算。
- 数字守卫只做存在性核对（「7 个工作日」必须能在证据里找到），不做语义推理——宁可误拦，误放就是赔付。

**追问预案**：「误拦了怎么处理？」——不重试，直接降级转人工，并记进 `kb_gaps` 池，人工审核后回流知识库。

## 六、多轮：为什么评测要按 session 隔离

**结论**：因为槽位会跨轮继承，这是正确行为。

- 第一轮问物流留下 `order_no=O10007`，第二轮问「能开发票吗」会带着这个订单号走写/读工具——这符合真人对话，不是 bug。
- 但它带来两个工程后果：评测必须每条用例独立 session（否则结果取决于执行顺序）；写操作用例会真实改库，所以 `runner._reset_world()` 每条用例前 `repo.reset()+seed()`。
- 这个坑我踩过：改地址用例第一次跑通过，第二次「确认」就落空——因为第一次已经把库里的地址改了，第二次预览返回「地址一致」。

## 七、成本与延迟怎么控

**结论**：级联 + 只缓存政策类。

- L0：订单/物流且工具结果齐全 → 模板直出，不调模型；L1：闲聊、高置信政策问答；L2：其余。
- 语义缓存只缓存 `policy` 和 `smalltalk`。**订单类答案绝不缓存**——同一个问法在不同订单下答案不同，缓存等于跨用户数据泄露；这是安全约束，不是性能取舍。
- `CostLedger` 记录每次调用的 tier/token/USD/延迟，p50/p95 与缓存命中率都能出数。

## 八、写操作为什么要二次确认和幂等

**结论**：因为「重复提交退货」和「改错地址」都是真金白银的损失。

- 预览 + `confirm=True` 才执行；幂等键是 `sha1(session|order|args)`，执行前查审计记录，重复请求返回上次结果；
- 越权与不存在都返回同一个 `order_not_found`，不给订单号探测的侧信道；
- 创建退货失败会回滚状态、删半成品、写 failed 审计——补偿逻辑写在工具里，而不是让编排层兜。

## 九、评测指标怎么读，有没有刷分

**结论**：四个维度一起看，且「不答」的比例也要看。

- `decision_accuracy` 单独看会被「全部转人工」骗过，所以同时看 `escalate_rate`（0.20）和 `clarify_rate`（0.17）——评测集里本来就放了 6 条应当转人工的用例（注入、投诉、越权、超范围）。
- `verify_pass_rate` 是自洽性指标：回答要通过自己的核验，防止「为了过用例故意把核验调松」。
- 切片按 `intent=` 和 `expect=` 两类输出，退化时能立刻定位到哪一类问题。

## 十、这套东西的短板

主动说，比被问出来好：

1. 评测集只有 30 条，是回归工具不是效果证明；
2. 中文分词是 bigram，领域词会碎，上线要换 jieba/pkuseg 并重训意图；
3. 主题收窄（`TOPIC_RULES`）是硬编码规则，靠评测驱动补，本质上是个「工程兜底」，长期应换成分类器；
4. 会话与缓存在进程内存，多副本要上 Redis；
5. 政策 DSL 不支持 OR/阶梯/地区维度；
6. 保形保证依赖可交换性，线上漂移会失效。

## 十一、如果给你更多时间

按投入产出排序：

1. **扩评测集到 300+ 条 + 对抗集**（同义改写、错别字、长尾类目），校准曲线才有意义；
2. **政策 DSL 升级**（OR、阶梯、版本 diff + 条款编辑器）；
3. **learning-to-defer**：用历史反馈训练「该转人工」的判别器，替代手写阈值；
4. **集合预测**：不只输出单一结论，输出候选集合，集合大于 1 就让用户澄清；
5. **可观测**：trace_id + 节点耗时 + 决策原因接 Langfuse/OTel，线上 badcase 回流 gap 池。

## 十二、几个可能被追问的细节

- **为什么自研图引擎不直接 LangGraph？** 需求只有「节点返回下一跳 + 条件分支」，自研 200 行、零依赖、可离线跑，且节点耗时/错误全在 `GraphEvent` 里，方便讲清楚一轮对话走了哪些步。生产里换 LangGraph 成本很低（节点函数签名一致）。
- **RRF 的 k=60 怎么来的？** 经验值，RRF 对 k 不敏感；真正影响效果的是「候选池取 top_k*4 再精排」。
- **为什么信息型条款要单独建模？** 「退款 1–3 个工作日到账」没有适用条件，如果当成资格条款，它会抢答所有问题并给出「你不符合条件」的错误结论。`policy_type` 在解析时自动推导，不靠人工标注。
- **claim 核验阈值 0.42 怎么定？** 在评测集上扫的：再低会把「模板寒暄」放进来，再高会误杀合规的正确回答。
- **注入检测为什么置信度 0.97？** 它是正则命中，确定性高于模型判断；宁可误拦成转人工，也不让模型看到注入文本。
