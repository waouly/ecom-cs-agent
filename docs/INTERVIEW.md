# 面试答辩手册：电商智能客服系统

> 用途：面试时被追问项目细节时，按这份手册的「结论 → 依据 → 取舍」三段式回答。
> 原则：**只讲你跑过的东西**，没跑过的（Milvus、BGE 精排、LangFuse）明确说「接口留好了、未实测」。
> 配套：`docs/DESIGN.md` 是设计推演，本文件是口语化答辩稿。

---

## 0. 60 秒电梯稿

> 这是一个电商售后客服的 AI 坐席。和常见「RAG + Prompt」的差别在于：我把**政策做成了可执行条件**，而不是让它去检索文本。每条政策是 DSL：`applies_to` + `conditions` + `exceptions`，规则引擎做三值判定（适用 / 不适用 / 信息不足），模型只负责把判定结果说成人话。判定为「信息不足」时系统追问，不适用时明确拒绝，只有适用且置信度够才自动答复——也就是 answer / clarify / escalate 三选一，而不是「总会答」。生成之后还有三层核验：逐句 claim 覆盖度、数字单位守卫、合规检查。政策类问题命中语义缓存，订单查询走 L0 模板直出，模型调用按 L1/L2 级联。30 条端到端用例上 decision / intent / clause / verify 四项都是 1.000，接 `deepseek-chat` 跑同一套用例结果一致，33 轮估算成本约 0.0077 美元。

## 1. 简历上这两行，怎么展开讲

简历原文：

- 面向电商售后咨询场景，支持售后政策问答、订单信息查询及证据不足时转人工。采用 RAG 与 Workflow、Agent 协作架构，完成问题分流、知识检索、业务工具执行与回答生成。
- 混合检索与评测：融合 BGE-M3 向量检索与 BM25 关键词召回，通过 RRF 合并结果并使用 BGE-Reranker 精排……

**展开时不要念简历，讲「我改了什么」**：

| 简历说法 | 实际实现 | 一句话亮点 |
| --- | --- | --- |
| RAG + Workflow + Agent | 自研状态图引擎（`graph/engine.py`）+ 五路由分发 | 没装 LangGraph，用 200 行实现同样的「确定性编排 + 条件分支」 |
| 政策问答 | 23 条结构化条款 + 三值规则引擎 | 政策不是文本，是可判定条件；模型不参与「能不能退」 |
| 混合检索 | 向量 + BM25 + RRF + 规则精排（含数字一致性惩罚） | 离线可跑，不依赖 Milvus/BGE 也能复现 |
| 证据不足转人工 | 三选一决策 + 生成后三层核验 | 校验在生成**之后**也有一层，这是上一版没有的 |

## 2. 一次请求的生命周期（讲系统时按这条线走）

```
guard → confirm → understand → cache → dispatch
                                   ├─ tools（读/写工具，L0 直出）
                                   ├─ retrieve → evaluate → generate → verify
                                   ├─ smalltalk
                                   └─ escalate
                                          ↓
                                       finalize
```

- **guard**：输入侧合规，拦截「导出所有用户手机号」这类批量数据请求。
- **understand**：归一化（退活→退货、zfb→支付宝）→ query 改写（别名 + 指代消解）→ 9 类意图 → 槽位抽取 → 五路由（policy / tool_read / tool_write / smalltalk / escalate）。
- **cache**：只缓存政策类（订单类绝不缓存，防跨用户泄露）。
- **dispatch**：按路由进工具 / 检索 / 闲聊 / 转人工。
- **evaluate**：查订单 → 构造 facts（类目、签收天数、是否拆封、是否定制…）→ 规则引擎三值求值 → 四信号置信度 → 概率校准 → 决策。
- **generate**：级联定 tier。L0 模板直出，L1 小模型，L2 大模型。
- **verify**：safety → claim → numeric，任一不过 → 降级转人工。
- **finalize**：写审计、记成本、超窗摘要、记录知识缺口。

**一句话总结**：编排是确定性的，模型只在「写答复」这一步出现。

## 3. 六个必问核心题

### Q1：为什么不用纯 RAG + Prompt？规则引擎不是不够灵活吗？

- 政策有明确的边界条件（7 天、未拆封、非定制），这些条件**不需要语义理解，需要判定**。让模型判断「签收 12 天能不能退」，它会给一个看似合理的答案，但它没有算术，也没有权威。
- 规则引擎给的是**可复现的判定 + 缺失字段**：不适用时能说清「哪一条不满足」，信息不足时能说清「缺哪个字段」——这正是追问话术的来源。
- 灵活性的代价放在模型侧：条款正文、例外说明、话术组织全部由模型（或模板）生成，规则只负责结论。
- 反过来说，纯 RAG 的失效模式很具体：检索到「7 天无理由」就答「可以退」，不管这单是不是定制、是不是已经拆封。规则引擎这一层就是堵这个。

### Q2：误放率 0、误拦率 15%，这个 0 可信吗？怎么定阈值？

- 前提先说清：这是**30 条自建用例**上的数，不是线上。样本量小，0 只能说明「这套用例里没有误放」，不能说明概率是 0。
- 阈值不是拍的：四信号（top1、margin、intent、tool 完整度）加权出 raw 分，Platt scaling 校准成概率，保形预测扫出满足 `risk ≤ α=0.05` 的最小阈值（0.529，coverage 0.60）。
- **为什么加 floor=0.5**：样本全对时 risk 恒为 0，阈值会退化到 0——「0 置信度也自动答复」。工程下限是必须的。
- 误拦的代价（多转一次人工）远低于误放（赔钱 + 客诉），这是业务定的不对称损失，不是技术偏好。

### Q3：置信度四个信号怎么来的？为什么不是直接用检索分？

- `top1`（最强证据的 rerank 分开根号）、`margin`（第一和第二的差距，差距小说明有歧义）、`intent`（意图置信度，分错了后面全错）、`tool`（工具完整度：该查的订单/物流/售后查到几个）。
- 只用检索分的问题是：它衡量「像不像」，不衡量「够不够」。一个 0.9 分的条款可能压根不适用这单。
- 加政策状态修正：applicable +0.12，not_applicable +0.04，unknown −0.10，无证据硬 cap 0.45。

### Q4：检索这块你踩过什么坑？

三个，每个都能展开：

1. **条款级切分 + 父子块**：小块（条款正文）用于召回，父块（文档概览 + 条款 + 例外）用于精排和生成，避免「召回准了但上下文残缺」。
2. **主题收窄比精排更重要**：同一订单会同时命中退货 / 发票 / 会员 / 价保条款。一开始以为精排能解决，实际「金卡会员有什么权益」被「物流停滞 72 小时」抢答。后来加了 `TOPIC_RULES`：先按问题里的主题词把候选桶收窄，**主题命中但桶里没有对应条款时返回空**——宁可没有，也不答非所问。
3. **数字一致性惩罚**：查询里有「3 天」，条款里只有「7 天」时降权。这条能防「问 3 天答 7 天」的错位。

### Q5：写操作（改地址 / 申请退货）怎么保证安全？

四件套，缺一不可：

- **二次确认**：第一次调用 `confirm=false` 只返回预览 + 幂等键，用户回「确认」才真正执行。
- **幂等**：同一请求重复执行不产生第二条售后单；用 `find_aftersale_by_idem` + 审计表 `payload LIKE` 双重判重。
- **越权**：`_require_order` 对「不存在」和「不属于你」返回同一个 `order_not_found`，避免用错误码探测别人订单。
- **审计与补偿**：每次写都落 `audit_log`；创建售后失败时回滚事务、删半成品、恢复订单状态，再抛业务错误。

### Q6：成本怎么控？为什么不缓存订单类？

- 级联：L0（工具直出，$0）→ L1（小模型，判定明确）→ L2（大模型，需要组织语言/多证据）。
- 缓存只对政策类开放：`CACHEABLE_SCOPES={"policy","smalltalk"}`。订单类答案包含金额、地址、物流，缓存跨用户就是泄露。
- 实测 33 轮（成本按内置 tier 价格表估算，不是账单）：L0 7 次 $0、L1 12 次 $0.0005、L2 14 次 $0.0072，合计 $0.0077，折 $0.00023/轮。

## 4. 高频追问清单（按难度递增）

1. 你的意图分类为什么不用模型？—— 用词典 + 样例句向量混合，离线可跑；9 类意图的边界比较清晰，模型收益不大，但接口留了。
2. 三值逻辑为什么不用布尔？—— 「签收 12 天 + 未说明质量问题」既不是可退也不是不可退，布尔会逼你二选一，三值能表达「缺信息」。
3. 什么时候判「确定性拒绝」而不是追问？—— 违反项里出现「已拆封」「定制」这类**结构性不满足**时直接拒绝；只是「超期」则追问质量问题（因为质量问题可以覆盖时效）。
4. 政策更新怎么上线？—— 基础 JSON 只读，增量写 overlay（`data/kb_overlay.json`），带审核人 / 时间 / 原因 / 关联 gap，可回滚；引擎启动时合并。
5. 知识缺口闭环怎么跑？—— 低置信 / 追问未解决 / 转人工的会话写 `kb_gaps`；`cli policy review` 人工审核后 `apply_update` 落 overlay；按 cluster 聚类看高频缺口。
6. 生成后核验误杀怎么办？—— 白名单按「语义事实」建：引擎算出的 satisfied / violated / 动作短语都登记进 `trusted`；「暂无记录」这类非断言直接跳过。
7. 你接真实模型后遇到什么问题？—— 见第 6 节故事一，这是最加分的题。
8. 延迟怎么保证？—— p50 6ms（大量命中 L0/L1 和缓存），p95 3.7s（L2 调用）。要更稳就加超时降级：L2 超时直接回模板。
9. 并发怎么做？—— 服务层无状态，会话存内存（可换 Redis）；SQLite 单写，生产换 PG；写操作靠幂等键兜并发重复提交。
10. 评测怎么防过拟合？—— 用例按行为口径写（不绑定具体措辞），切片看 intent / expect 两类；数据集与规则同时演进时，每次改规则都要重跑全量看退化。
11. 你只有 30 条用例，说服力在哪？—— 不宣称泛化，宣称「可回归」：改一行规则能立刻看到哪类退化，这在客服这种规则密集场景比大 benchmark 更实用。
12. 如果用户说「我不管规定，我就要退」？—— 规则引擎判 reject，但 escalate 分支允许人工兜底；系统不承诺做不到的事。
13. 合规上有什么设计？—— PII 脱敏、禁止过度承诺、提示注入检测（8 条模式）、批量数据请求拦截、越权统一错误码。
14. 为什么自研图引擎？—— 环境没装 LangGraph，且这个流程是确定性编排，自研 200 行可控可测；节点返回下一个节点名，条件边查路由表。
15. 会话上下文怎么管？—— 三层：raw window（最近 6 轮）+ 分段摘要 + 结构化槽位（订单号、地址这类必须精确保留）；工具结果裁剪后再进上下文。
16. 你项目里最不满意的部分？—— 检索仍是混合检索 + 规则精排，BGE reranker 只写了适配器没实测；用例规模小；没有线上流量做 A/B。
17. 上生产还要做什么？—— 见第 8 节。
18. 这个项目最难的地方？—— 不是模型调用，是「判断什么时候不该答」。三选一决策、三值逻辑、核验降级，本质都是同一件事。
19. 你怎么验证「不答」是对的？—— 用例里显式标注 expect=escalate / clarify，误答和误拒都能被单独统计。
20. 代码量？—— 约 6600 行 Python，66 个模块，54 个单测，30 条端到端用例，2 份文档。

## 6. 三个可以讲的故事（面试官最爱听失败）

### 故事一：接上真实模型，指标从 1.000 掉到 0.967

- 现象：mock 全绿，接 `deepseek-chat` 后 decision 0.967、verify 0.833。
- 定位：失败用例的**结论全对**，是模型在结论后补「如信息不足，建议转人工」「我无法核实订单状态」——系统已判 answer，它在替系统改判；另有动作短语「可申请全额退款」不在核验白名单里。
- 修法：生成侧把模型定位成「撰写器」（禁止改判/禁止建议转人工）+ 整句删除越权话术；核验侧把动作短语登记为可信事实。
- 坑中坑：清理函数一开始用 `split_sentences` 切句再拼接，结果逗号被吞、回复变成无标点粘连长句——改成整句正则替换、保留标点。
- 收获：核验层的白名单要按「语义事实」建，不能按「模板句式」建；否则换个模型就全废。

### 故事二：「金卡会员有什么权益」被「物流停滞 72 小时」抢答

- 现象：主题对不上，但 rerank 分更高。
- 根因：同一订单的候选条款里有退货、发票、会员、物流，精排只比「相关性」，不比「问的是哪类事」。
- 修法：`TOPIC_RULES` 先按主题词收窄候选桶，桶里没有就返回空；再退化为信息型回答。
- 教训：**检索系统的排序目标，和业务要的「答对题」不是一回事**。

### 故事三：改地址的「确认」永远弹不出来

- 现象：评测里 confirm 用例第二次跑必挂。
- 排查：直接调工具发现 O10010 的地址已经变成上一条用例写进去的值——写操作真实落库，第二次 replay 时地址已一致，工具走「无需修改」短路，没有 pending，「确认」自然落空。
- 修法：评测每条 case 前重置世界（`repo.reset()` + `seed`），并重置 session store，做用例级隔离。
- 教训：**有副作用的系统，测试隔离不是洁癖，是正确性的一部分**。

## 7. 诚实说不足（主动说比被问出来好）

- 用例只有 30 条，指标不是泛化能力证明，只是回归基线。
- 真实适配器里只实测了 OpenAI 兼容 LLM；BGE embedding、cross-encoder 精排、Milvus 只写了接口，因环境无 torch / pymilvus 未跑过。
- 没有 Web 前端（明确不做），演示走 CLI 和 FastAPI。
- SQLite 单机、会话在内存，生产要换 PG + Redis。
- 中文数字（「三天」）数字守卫不覆盖，靠归一化前置。
- 意图识别是词典 + 样例向量，长尾表达会掉。

## 8. 如果面试官问「上生产还要做什么」

按优先级：

1. **真实政策接入**：现在 23 条是仿真的，真政策条款更碎、时效版本更多，需要条款版本迁移策略和灰度。
2. **数据面**：政策库接 CMS / 审核流；订单数据接真实订单服务；`kb_gaps` 接运营看板。
3. **观测**：把 trace（每轮节点耗时、证据、核验结果）接 Langfuse 或自建，按决策类型做看板；报警看 verify 失败率和 escalate 率突变。
4. **并发与存储**：会话迁 Redis，DB 迁 PG，写操作加分布式锁（幂等键保留）。
5. **模型侧**：L1 换成小模型或本地模型，L2 加超时降级；prompt 版本化管理。
6. **评测扩充**：用例从 30 扩到几百条，加对抗集（诱导承诺、越权、注入），LLM-judge 与人工标注算一致性 κ。

## 9. 现场 demo 脚本（3 分钟）

```powershell
cd ecom-cs-agent
$env:PYTHONIOENCODING="utf-8"

# 1) 全链路（离线）
python -m ecom_cs.cli demo

# 2) 端到端评测
python -m ecom_cs.cli eval

# 3) 单测
python -m unittest discover -s tests

# 4) 交互（可选真实模型：设置 ECOM_CS_LLM_* 四个环境变量）
python -m ecom_cs.cli chat
```

演示时按这个顺序讲三句话：

1. 「这条能退」——展示条款 ID、满足的条件、订单事实。
2. 「这条要追问」——O10002 超期，系统问「是否有质量问题」，而不是直接判死。
3. 「这条要写库」——改地址先预览、回「确认」才执行，再重复一次看幂等。
