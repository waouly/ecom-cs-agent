# 设计文档：把「会检索」的客服改造成「能处置」的客服

本文记录这个工程**为什么长成这样**：每一处与常见 RAG 客服不同的地方，都先写清原方案会错在哪，再写这一版怎么绕开，最后写代价。代码注释只解释局部，整体取舍在这里。

---

## 0. 一句话诊断

原系统在优化「信息获取」，而客服业务买的是「处置结论」。

用户问「我这单能退吗」，需要的不是一个相似度 0.86 的段落，而是四个确定性答案：

1. 适用哪条政策（条款 ID）；
2. 条件逐条是否满足（含缺失事实）；
3. 结论是什么（可退 / 不可退 / 需要补充信息）；
4. 下一步动作（提交退货单 / 追问 / 转人工）。

这四件事里只有第 1 件勉强算检索问题。所以改造的主线是：**把政策变成可执行条件，把回答变成可核验产物，把「答/不答」变成三选一决策。**

---

## 1. 政策：从「被检索的文本」到「可执行条件」

### 原方案的问题

- 条款是长文本，检索到之后由模型自由发挥，「7 天」到底从签收算还是从支付算、已拆封算不算，全靠模型这次读得细不细；
- 同一条款在不同问法下结论可能不一致（今天说能退、明天说不能），这是客服最忌讳的；
- 无法回答「缺哪个信息」，只能笼统地说「请提供更多信息」。

### 这一版

`configs/policies/*.json` 里每条条款是：

```json
{
  "clause_id": "RET-7D-003",
  "applies_to": {"category": ["digital"]},
  "conditions": [
    {"field": "days_since_sign", "op": "<=", "value": 7, "label": "签收后天数不超过 7 天"},
    {"field": "opened", "op": "==", "value": false, "label": "商品未拆封"}
  ],
  "exceptions": [
    {"exception_id": "E1", "when": [{"field": "has_quality_issue", "op": "==", "value": true}],
     "action": "refund_full", "text": "存在质量问题的按质量问题退货处理"}
  ],
  "action": "refund_full"
}
```

规则引擎 `PolicyEngine.evaluate` **三值求值**：条件为真 / 为假 / **未知（缺事实）**。这个「未知」是整套设计的支点：

- 未知 → `UNKNOWN` → 追问缺的那个字段（`missing` 里带着字段名）；
- 为假 → `NOT_APPLICABLE` → 直接给否定结论（但要区分「确定性拒绝」和「可能还有别的路」）；
- 为真 → `APPLICABLE` → 给结论 + 条款 ID + 满足的条件列表。

**关键细节：确定性拒绝 vs 需要追问。** O10003（数码、已拆封）应当直接答「不能无理由退」，而不是追问「有没有质量问题」；但 O10002（签收 12 天）应当追问，因为超期仍可能走质量问题退货。实现上引擎看**违反项**：`definitive = any("拆封" in v or "定制" in v for v in violated)`，确定性违反直接拒绝，其余在例外未知时回退到 `UNKNOWN`。

**条款分两类。** `policy_type = eligibility | info`：没有条件、也没有适用类目的条款（「退款 1-3 个工作日到账」）只能提供信息，不能当资格依据。否则「退款多久到账」会被某条毫无关系的资格条款抢答成「请提供商品类目」。这个 `policy_type` 在解析时就推导出来，不靠人工标注。

### 代价

- 政策要有结构化建模能力，新增条款要写 DSL，而不是往文档里加一段话；
- 复杂政策（阶梯、多条件组合、地区差异）需要更强的表达式，当前只支持 AND + 简单例外；
- 事实必须能落到字段（`category / opened / days_since_sign …`），否则永远是 `UNKNOWN`。

## 2. 决策：answer / clarify / escalate 三选一

### 原方案的问题

只有「答」和「转人工」两条路。缺信息时要么硬答（幻觉温床），要么直接转人工（把本可以问一句解决的事推给人工）。

### 这一版

`n_evaluate` 的决策顺序（顺序本身就是设计）：

1. 缺订单号且问题必须知道订单 → `clarify`；
2. 订单不存在 / 越权（同一错误码 `order_not_found`，避免订单号探测）→ `escalate`；
3. 注入/投诉路由 → `escalate`；
4. 只读工具齐了 → `answer`；
5. 政策 applicable / not_applicable → `answer`；
6. 政策 unknown 且有缺失字段 → `clarify`（最多问 2 个字段）；
7. 无任何证据 → `escalate`；
8. 最后才用校准阈值兜底。

追问用 `FIELD_QUESTIONS` 把字段翻成人话（「商品现在拆封了吗」），且**先讲规则再问**：用户问的是规则，你不能一句「请提供订单号」了事。

### 代价

- 多轮里槽位会累积，可能出现「上一轮查物流的订单号被这轮的问发票继承」——这是多轮上下文的正确行为，但评测必须按 session 隔离用例，否则结果取决于执行顺序；
- 追问字段选错会显得机械，所以「最多问 2 个」+ 主题收窄一起用。

## 3. 检索：为「规则问答」服务的混合检索

保留 BM25 + 向量 + RRF + 重排，因为政策问答确实是检索问题；但补了三处原方案的欠账：

1. **父子块**：检索块是条款正文，精排/生成用父块（文档概览 + 条款 + 例外文案）。小块命中率高，大块上下文全。
2. **改写与指代消解**：`zfb` → 支付宝、`退到哪` → 退款到账渠道、`这个订单` → 订单号。别名表本身是评测驱动的——每加一条失败用例就补一条别名。
3. **生效期过滤**：`effective_from/effective_to`，过期条款不参与召回。政策改版时旧答案不会诈尸。

### 一个反直觉的教训

**主题收窄比精排更重要。** 同一订单会同时命中退货、发票、会员三条资格条款，单纯按「谁更具体（有无类目）」排序仍会答错题。所以 `n_evaluate` 先按 `TOPIC_RULES` 把候选收窄到与问句主题一致的那一桶：

- 命中主题词但桶里没有对应条款 → **返回空**，宁可没有，也不拿「发货时效」回答「改地址」；
- 命中词的**长度**作为具体度：问「补差价」时「价格保护」优先于「价保」。

这条规则修掉了「问会员权益答成物流停滞」这类问题，比调 rerank 权重有效得多。

### 代价

`TOPIC_RULES` 是硬编码规则，新增业务主题要手写一条；它是「评测驱动的工程兜底」，不是通用方案。长期应替换成训练过的意图-主题分类器。

## 4. 生成后核验：回答必须逐句有出处

### 原方案的问题

只在生成前做证据校验（置信度够了就答），生成后完全裸奔。模型把「7 天」说成「15 天」、把审核时效说到账时效、把「可以申请」说成「我们保证全额退」——这些都在置信度检查之外。

### 这一版三层

1. **claim 级核验**（`verify/claims.py`）：把回复切成句子，逐句算与证据的覆盖度。两类特殊处理：
   - 条款 ID 出现在句子里 → 直接 0.85（引用就是强证据）；
   - 规则引擎/工具产出的短语进 `trusted`，命中即 `engine_fact`（1.0）。
   为什么需要 `trusted`：只拿检索证据比对，会把「当前订单不满足『商品未拆封』」「因此您可以申请全额退款」这类**由引擎算出来的正确结论**全部误杀。核验器要能区分「模型编的」和「引擎算的」。
2. **数字守卫**（`verify/numeric.py`）：回复里的「数字+单位」必须能在证据/工具数据/槽位里找到。只做存在性核对，不做语义对齐——宁可误拦，误放就是赔付。
3. **合规**（`verify/safety.py`）：PII 脱敏（手机/身份证/银行卡/邮箱）、过度承诺（保证/100%/绝对/永久）、系统提示泄露、批量数据请求。

不通过时不是重试，而是**降级为转人工**：客服场景里「说错」的代价远高于「没答」。

### 代价

- 覆盖度是近似指标，长句/同义表达会误杀，所以有 `SKIP_PREFIXES`（「暂无记录」这类不是断言）和 `trusted` 两处人工口子；
- 数字守卫对中文数字（「三天」）不生效，需要归一化后再核对。

### 接上真实模型之后，这一层暴露了两个真问题

离线 mock 时核验层看起来「工作良好」，接 `deepseek-chat` 跑同一套 30 条用例，第一轮就掉到 decision 0.967 / verify 0.833。原因不是模型答错了结论——结论全部正确——而是它**在正确结论之外多说了一句**：

1. **越权话术**：模型喜欢在结尾补「如信息不足，建议转人工」「我无法核实该订单状态」。系统明明已经判了 answer，它在替系统改判。修法：`_SYSTEM_PROMPT` 里把它定位成「答复撰写器，判定已由规则引擎完成，不得改判、不得建议转人工」；再加一道生成后清理 `clean_llm_reply()`，整句删除含「信息不足 / 建议转人工 / 无法核实 / 需要更多信息 / 请提供订单号」的句子。注意**不能用 `split_sentences` 切开再 `''.join`**——那个函数对超长句按逗号切分且丢弃分隔符，拼回去会得到没有标点的粘连长句，要按整句正则直接替换、保留原文标点。
2. **可信事实漏登记**：模型写「可申请全额退款」，模板写「因此您可以申请全额退款」。`trusted` 只登记了后者，模型的说法被覆盖度判成 low_overlap。修法：`trusted` 同时登记动作短语本身。这条教训可以一般化——**核验器的白名单要按「语义事实」而不是「模板句式」来建**，否则换个模型就全废。

还有一个更隐蔽的：信息型条款（价保、会员权益）回答时，模型会说「您的订单签收后不超过 15 天，可申请价保」。这是在用规则文本对具体订单下断言，而这条规则本来不挑订单。修法是在渲染上下文里显式禁止「您的订单…」「您可以…」句式，并把 `info_only` 从「只转述」升级为硬约束。

修完之后真实模型与 mock 指标完全一致（四项 1.000）。这说明核验层不是「给模型擦屁股」，而是把「模型自由发挥的空间」钉死在可验证的事实上；模型越强，这层越省事，但只要它还有「补一句」的冲动，这层就不能省。

## 5. 置信度：从拍阈值到概率校准 + 保形阈值

### 原方案的问题

四信号加权和直接和 0.62 比。问题是这 0.62 没有概率含义，改权重就得重调阈值，调完也不知道「自动答复里到底错多少」。

### 这一版

1. **四信号融合**：top1 相关性、top1 与 top2 的 margin、意图置信度、工具完备度；政策状态加减分（applicable +0.12 / not_applicable +0.04 / unknown -0.10）；无证据直接 cap 0.45。
2. **Platt 校准**：用评测集的 `(融合分, 是否答对)` 拟合 `sigmoid(a·x+b)`，把融合分变成答对概率。
3. **保形阈值**（`SelectiveThreshold.fit`）：按置信度降序扫前缀，取满足「错误率 ≤ alpha」的最小阈值。样本全对时风险恒为 0，公式会退化成「0 分也自动答」，所以加 `floor=0.5` 的工程下限。

`python -m ecom_cs.cli calibrate` 一条命令重拟合，写出 `configs/calibration.json`。

### 代价

- 30 条样本拟合出来的校准曲线**不可当真**，它证明的是「流程通了、指标可复现」，不是「概率准」。上线要几百到几千条带标注样本；
- 保形保证依赖可交换性，线上分布漂移后会失效，需要滚动重拟合 + 监控覆盖率。

## 6. 成本与延迟：级联 + 只缓存政策类

客服的命门是延迟和单均成本，不是模型上限。`Cascade.decide`：

- 闲聊 → L1；
- 订单/物流且工具全 ok → **L0 模板直出**（不调模型）；
- 政策 applicable 且校准置信度 ≥ 0.78 → L1；
- 其余 → L2。

`SemanticCache` 只缓存 `policy / smalltalk` 两类。**订单类答案绝不进缓存**：同一个问题「我的退款到哪了」在不同订单下答案不同，缓存会造成跨用户信息泄露。

`CostLedger` 记录每次调用的 tier、token、USD、延迟，`stats` 里能看到 p50/p95 与缓存命中率——面试里「你怎么算成本」有据可查。

### 代价

级联的阈值是启发式；L0 直出要求模板覆盖所有工具字段，字段一变模板就要跟着改（这也是为什么不建议在 L0 做复杂改写）。

## 7. 写操作：只会答的客服不是客服

三个写工具（改地址、创建退货、转人工）都带四件套：

1. **二次确认**：`confirm=False` 只返回预览 + 幂等键，用户回「确认」才执行；
2. **幂等**：`sha1(session|order|args)` 前 16 位，执行前查 `audit_log`，重复请求返回上一次结果；
3. **越权**：订单不属于当前用户与订单不存在返回同一个 `order_not_found`，不给探测侧信道；
4. **失败补偿**：创建退货失败时回滚状态、删掉半成品记录、写 failed 审计，再抛错。

写操作链路此前是**死代码**（工具写了但编排层不调用）——这也是「评测集只测问答」的盲区。补上后新增了一条确认轮用例，链接通了。

## 8. 评测：从检索指标到端到端

30 条用例，每条判 4 件事：`decision` / `intent` / `clause` / `verify`。指标：

- `decision_accuracy`：决策正确率（answer/clarify/escalate）；
- `clause_hit`：引用条款正确率；
- `verify_pass_rate`：回答通过核验的比例（不过说明生成或核验有矛盾）；
- `escalate_rate / clarify_rate`：两个「不答」的比例，防止用「全部转人工」刷 decision；
- 按 intent 与 expect 两类切片，能看出退化集中在哪类问题。

跑评测时**每条用例重置业务库**（`repo.reset() + seed()`）：写操作用例会真实落库，不隔离的话第二条 replay 就看不到预览，结果取决于顺序。这个坑踩过一次，测试从「偶尔失败」变成「稳定通过」。

### 指标口径的自我约束

- 不把「30 条全过」当成效果证明；它证明的是链路正确、回归可查。
- `escalate_rate 0.2` 不是越低越好：评测集里本来就放了 6 条应当转人工的用例（注入、投诉、越权、超范围）。

## 9. 踩过的坑（写给下一个改这个仓库的人）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 所有回答都被「无法核实」拦住 | 模板还在用旧工具名，兜底 `json.dumps` 把整段数据塞进回复，触发数字守卫 | 模板按真实工具字段渲染，禁止 dump JSON |
| 有订单号却仍走政策问答 | 槽位合并后没有重新读 `order_no` | 合并后重读，再决定路由 |
| 物流问题莫名追问「商品类目」 | 把编排层 `TurnContext` 当 `ToolContext` 传进工具，工具抛异常 | `_tool_ctx()` 构造正确的 `ToolContext` |
| 「签收三天了能退吗」被判成物流 | 主题规则里放了「签收」 | 主题词收窄，物流只认「物流/快递/派送/运单/包裹」 |
| 「退款多久到账」被追问质量问题 | 资格分支优先于时效信息分支 | `timing`/非资格问法优先信息型条款 |
| 正确结论被判无依据 | 核验只看检索证据 | 引擎满足/违反项 + 工具短标量进 `trusted` |
| 第二遍跑评测就不对 | 写操作真实落库，用例间互相污染 | 每条用例重置库 + 隔离 session |
| 改 .py 后中文全乱 | 用 PowerShell `Set-Content` 写 UTF-8 文件 | 只用编辑器/edit 工具改源码 |

## 10. 如果继续做

1. **政策 DSL 升级**：支持 OR、阶梯条件、地区维度；配一个条款编辑器 + 版本 diff。
2. **保形预测做集合预测**：不只给「答不答」，而是给「候选结论集合」，集合大于 1 就追问或人工。
3. **learning-to-defer**：用历史反馈训练「这条该转人工」的判别器，替代手写阈值。
4. **评测扩到 300+ 条**并做对抗集（同义改写、错别字、长尾类目），校准曲线才有意义。
5. **多副本**：会话与语义缓存上 Redis，写操作幂等键上 Redis SETNX。
6. **可观测**：把 `trace_id`、节点耗时、决策原因接到 Langfuse/OTel，做线上 badcase 回流进 gap 池。
